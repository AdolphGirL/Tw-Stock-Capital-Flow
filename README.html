專案簡介

本 App 是一套專為台灣股市一般投資人設計的板塊資金流向監控與量化決策系統。底部導覽列共 3 個分頁：大盤診斷、資金佔比（板塊資金佔比異動）、領先雷達。

傳統看盤工具只告訴你今天哪支股票漲最多，但無法回答：

主力集中哪裡？
今日資金正往哪個板塊集中
週期在哪？
上漲是點火還是即將出貨
潛伏訊號？
股價底部但主力已悄悄建倉
資金集中度變了？
今日成交值佔比明顯偏離近期均值的板塊
資料來源：臺灣證券交易所（TWSE）/ 證券櫃檯買賣中心（TPEX）開放資料。所有運算皆在設備本地端執行，不上傳任何個人資料。

板塊資金佔比異動 Tab 1

計算每個大類股今日成交值佔大盤/櫃買總成交值的比重，與過去最多 5 個交易日的平均比重相比，偏移達門檻即標註——直接反映「今天錢實際往哪個板塊集中」，取代原本以 trendStrength 做 Z-score 統計的異常偵測器。

運算邏輯

今日比重 = Σ(板塊內個股成交值) / 當市場總成交值 × 100 過去均值 = 過去最多 5 個交易日「同板塊比重」的平均（至少需 3 天樣本） deviation = 今日比重 − 過去均值比重　　（百分點差，非相對百分比） deviation ≥ +5pt → 佔比顯著上升（資金集中度上升，紅色） deviation ≤ −5pt → 佔比顯著下降（資金關注度降溫，綠色）

資料來源

直接讀取本地最近 6 天的原始股票快照（listed_*.json / otc_*.json，今日 + 最多 5 天歷史），不依賴 SQLite 歷史表，因此不受 SQLite 歷史表清理影響。注意：一鍵重置會連原始快照一併刪除，重置後需重新累積至少 3 個交易日才會再出現結果。

畫面呈現

  • 歷史樣本不足 3 天時，整頁顯示「歷史資料累積中」與 1/2/3 天的累積進度方塊。
  • 摘要卡顯示：分析板塊數、今日總成交值（億）、異動訊號數。
  • 「佔比顯著上升」（紅）與「佔比顯著下降」（綠）兩段，各自依偏移幅度排序；卡片顯示 過去均值% → 今日%、樣本天數與偏移條（滿格 = 15pt），點擊進入該板塊細類頁。
  • 僅分析該市場的大類板塊，且該板塊在歷史中至少要有 3 天樣本才列入。

訊號異動通知

於冷啟動（含命中快取與離線快取）、App 從背景回前景且抓到新資料時自動執行，同時觸發 App 內 Dialog 與系統本地推播通知。手動重新整理不會觸發偵測。

  1. 讀取個人觀察清單；若清單為空，完全跳過（零額外運算）
  2. 載入 signal_snapshot 表的上次訊號記錄
  3. 以 MomentumStrategy 重新計算今日訊號，與上次記錄比對：只要訊號不同就算異動；等級 買進(3) > 續抱(2) > 觀望(1) > 出清(0)，用來判斷升級 ↑ / 降級 ↓
  4. 新加入清單、尚無上次記錄的板塊，第一次也會通知（「開始追蹤，當前訊號：…」）
  5. 儲存今日訊號作為下次比對基準
  6. 若有異動：彈出 App 內 Dialog（升級排最前、首次追蹤次之、降級最後）+ 推送一則彙整的系統本地通知（iOS / Android）

核心演算引擎

1. CapitalFlowEngine — 個股資金流引擎

計算每支個股今日資金流分數，作為板塊層級計算的原子輸入。N = 本地最近最多 5 個交易日快照（loadRecentSnapshots(5)，含今日）。

── 成交量比（volumeRatio）───────────────────────────── volumeRatio = today.value / avg(N-day value) (均值含今日) ── 動能分數（momentumScore）────────────────────────── volatility = (high − low) / close × 100 momentumScore = changePercent × 0.7 + volatility × 0.3 ── 延續分數（persistenceScore）─────────────────────── persistenceScore = today.changePercent × (positiveDays / totalDays) ── 綜合資金流分數（flowScore）──────────────────────── flowScore = volumeRatio × 0.35 + momentumScore × 0.40 + persistenceScore × 0.25 ── 流向判定 ──────────────────────────────────────────── flowScore > 1 → inflow flowScore < −1 → outflow → neutral

板塊層級聚合（CapitalFlowAnalyzer → CategoryUiModel）

大類與細類板塊皆依市場分開聚合，這些欄位驅動大盤卡片、板塊卡片、排序與 30 日走勢圖：

dayK = mean( 該板塊個股 flowScore, 第 K 個交易日 ) (K = 1 今日, 2 昨日, 3 前日) score = day1 persistence = (day1 + day2 + day3) / 3 trendStrength = (day1×0.5 + day2×0.3 + day3×0.2) + ((day1 − day2) + (day2 − day3)×0.5) marketScore = mean( 該市場所有個股 flowScore ) (首頁大盤卡片分數)

個股篩選：只納入 4 碼且非 00 開頭的代碼（排除 ETF 等）；changePercent = change / (close − change) × 100（以昨收為分母，與 Yahoo 一致）；類股對照來自 assets/stock_mapping.txt，查無對照者歸入「其他」。

2. MainstreamEngine — 主流方向引擎

聚合個股至板塊層級，計算主流資金強度分數（需至少 3 天資料計算延續力）。

各市場獨立運行：上市 上市 的 MainstreamEngine 只處理上市股票，上櫃 上櫃 同理，確保跨市場板塊名稱不互相干擾。
flowScore = mean( changePercent × value/億, per stock ) persistenceScore = day1×0.5 + day2×0.3 + day3×0.2 (近3日衰減加權) diffusionScore = riseCount / totalCount × 100 leaderScore = leader.value/億 × 0.6 + leader.changePercent × 0.4 mainstreamScore = flowScore×0.35 + persistenceScore×0.30 + diffusionScore×0.20 + leaderScore×0.15

此引擎輸出的 flowScore／diffusionScore 是 LifecycleEngine 計算 hotMoneyIn（flowScore > 0 AND diffusionScore > 45）的輸入來源，實際判斷邏輯在 LifecycleEngine 內執行。

3. TrendMetricsEngine — 趨勢指標引擎

對任意時序數列計算四個趨勢特徵，供 LifecycleEngine 使用。

slope = vₙ − v₀ (頭尾差) acceleration = (vₙ − mid) − (mid − v₀) (後段加速 − 前段加速) volatility = mean( |vᵢ − avg| ) stability = 100 − volatility

4. LifecycleEngine — 生命週期引擎

對每個板塊以最近 5 日快照建立 3 條時間序列（分數 = mean(漲跌幅×成交值/億)、流量 = mean(成交值/億)、擴散 = 上漲家數%），透過 TrendMetricsEngine 取得趨勢特徵，依規則判定所屬生命週期階段。

兩種執行方式：BootstrapAnalyzer 會跑一份「上市＋上櫃混合」的 LifecycleEngine（Phase 2，結果為 lifecycles），以及上市、上櫃各自獨立的實例（Phase 1 _runLifecycleForMarket，結果為 listedLifecycles / otcLifecycles）。目前實際被使用的是混合版（觀察清單訊號、訊號異動通知、SQLite lifecycle_history）；分市場版只寫入分析快取，暫無 UI 使用。詳見 上市/上櫃分離架構。

hotMoneyIn = mainstream.flowScore > 0 AND mainstream.diffusionScore > 45（取自 MainstreamEngine 輸出）也是在此引擎計算，供 MomentumStrategy 判斷用。

優先階段判斷條件（簡）
1死亡 (Dead)score < 10 AND slope < 0 AND flow < 0
2退潮 (Decline)slope < 0 AND accel < 0 AND flow < 0
3出貨 (Distribution)score > 70 AND accel < 0 AND volatility > 15
4狂熱 (Euphoric)score > 85 AND diffusion > 75 AND volatility > 20
5主升 (Markup)score > 60 AND slope > 20 AND stability > 70 AND volatility < 18
6擴散 (Expansion)diffusion > 45 AND slope > 10 AND flowTrend.slope > 0
7點火 (Ignition)accel > 5 OR flowTrend.accel > 0
8盤整 (Consolidation)（以上條件皆不符）

5. MomentumStrategy — 動量決策策略

無獨立瀏覽頁面：原本的「動量決策」瀏覽頁已下線（見 功能異動說明），此引擎現在只服務於觀察清單訊號顯示與訊號異動推播，不再提供「瀏覽全部板塊訊號」的畫面。
① 結構性 SELL（最高優先，無條件出清） stage ∈ {distribution, decline, dead} ② BUY — 點火試單 stage == ignition AND hotMoneyIn AND acceleration > 0 ③ BUY — 主升全面加碼 stage ∈ {expansion, markup} AND hotMoneyIn AND diffusion ≥ 50.0 ④ HOLD — 鎖籌續抱 hotMoneyIn AND persistence ≥ 40.0 （若 stage == euphoric，改為「狂熱期・禁止追高」：可續抱但禁止加碼） ⑤ SELL — 動能渙散（雙殺條件） !hotMoneyIn AND persistence < 40.0 ⑥ NEUTRAL — 盤整觀望

關鍵設計：SELL 需兩項同時惡化，避免在橫盤整理時誤殺部位。

6. RotationEngine — 輪動引擎

比較今日與昨日各板塊資金流分，計算資金在板塊間的搬移路徑（依市場分開執行，至少需 2 個交易日快照）。

categoryScore = mean( changePercent × value/億, per stock ) diff = todayScore − yesterdayScore diff > 0 → 流入板塊 diff ≤ 0 → 流出板塊 流入、流出板塊各自依 |diff| 由大到小排序，按名次一對一配對 （第 1 大流出 ↔ 第 1 大流入、第 2 ↔ 第 2 …），配對數 = 兩邊較少者 rotationScore = ( |outflow_diff| + |inflow_diff| ) / 2

7. RotationLeadingAnalyser — 領先分析器

inflowSum = Σ rotationScore（此板塊為流入方） outflowSum = Σ rotationScore（此板塊為流出方） feederCount = 有多少不同板塊正在向此板塊輸血 RNM = inflowSum − outflowSum RNM ≥ 45 AND feederCount ≥ 2 → 🟢 強力吸籌 RNM > 15 → 🍏 溫和流入 −15 ≤ RNM ≤ 15 → ⚪ 中性觀望 RNM < −15 → 🟠 派發風險 RNM ≤ −45 → 🔴 大量出逃
已知限制：由於 RotationEngine 採名次一對一配對，每個板塊在單日輪動結果中最多只會以「流入方」或「流出方」出現一次，因此 feederCount 實際上最多為 1、且同一板塊的 inflowSum 與 outflowSum 必有一個為 0——目前「🟢 強力吸籌」評級（需 feederCount ≥ 2）在實務上不會出現，RNM ≥ 45 的板塊會落在「🍏 溫和流入」。

8. MarketSentimentEngine — 市場情緒引擎

以上市＋上櫃混合的最新快照與混合版 mainstreams 計算，結果顯示於首頁「市場熱錢情緒」卡片。

riseRatio = 上漲家數 / 總家數 (0–1 的比例) strongCategoryCount = mainstreamScore > 30 的板塊數 mainstreamAverage = mean( mainstreamScore ) hotMoneyStrength = mean( value/億 × changePercent, per stock ) score = riseRatio × 30 + strongCategoryCount × 8 + mainstreamAverage × 0.35 + hotMoneyStrength × 0.25 score ≥ 85 → 過熱警惕 score ≥ 65 → 資金樂觀 score ≥ 40 → 中性觀望 score ≥ 20 → 偏空悲觀 else → 市場恐慌

9. TurnoverShareShift — 板塊資金佔比異動

取代原本以 trendStrength 做 Z-score 統計的異常偵測邏輯，改為直接量測「今天錢實際往哪個板塊集中」。

todayWeight = Σ(板塊內個股 value) / 當市場當日總 value × 100 avgWeight = mean( 同板塊過去最多 5 個交易日的 todayWeight ) deviation = todayWeight − avgWeight　　（百分點差，非相對百分比） deviation ≥ +5pt → 佔比顯著上升 deviation ≤ −5pt → 佔比顯著下降 最少樣本：≥ 3 天歷史 最大回溯：5 天（受原始快照僅保留 7 天限制）
不吃 SQLite 歷史：直接讀取 HistoryRepository 保留的最近 6 天原始股票快照（listed_*.json / otc_*.json）即時計算，不依賴 category_history 表，因此不受 SQLite 歷史清理影響——只要原始快照天數足夠即可算出均值（一鍵重置會連原始快照一起刪除，需重新累積）。此邏輯目前直接寫在 turnover_share_page.dart 內，未抽成 domain 引擎。
市場分流天生正確：直接以每筆 StockData.market 過濾加總，不像舊版 AnomalyDetector 需要額外用 object identity 修正同名板塊誤判問題。

10. StockScanner — 個股掃描器

closePosition = (close − low) / (high − low) intradayReturn = (close − open) / open × 100 命中 = changePercent > 0 AND closePosition ≥ 0.7 AND intradayReturn > 0 high == low（一字線）時 closePosition 以 0.5 計 → 不命中

邏輯直接寫在 sub_category_page.dart（_passesScanner），未抽成獨立引擎類別。

資料同步與更新機制 NEW

背景：TWSE / TPEX 官方開放資料實際整理完成的確切時間點無法得知（可能傍晚就緒，也可能延到隔天）。與其用一個猜測的精確時間點決定何時抓取，不如鎖定「確定沒有新資料」的區間直接略過、其餘時間都允許嘗試，並讓使用者隨時能自行手動刷新取得最新狀況。

白天靜默期（08:00–18:00）

SyncManager.syncTodayData() 每次啟動 App 時執行，邏輯如下：

時段 / 條件行為原因
08:00–18:00（白天靜默期）略過 API 呼叫，直接使用本地快照台股收盤 13:30，此區間內確定不會有新收盤資料，是唯一有把握的判斷依據
18:00～隔日 08:00（靜默期以外）一律嘗試向 API 抓取官方實際整理完成時間不確定，抓不到新資料只是白跑一趟、不會寫壞本地資料，因此不再猜測精確時間點
本地資料超過 3 個日曆天無論在不在靜默期，強制向 API 同步避免連假／網路異常後資料一直停留在舊快照
手動刷新（forceSync）完全略過以上護欄，直接呼叫 API使用者主動要求最新資料時的最高優先權
時間護欄只負責「要不要嘗試」，不影響資料正確性：快照檔以 API 回傳的實際交易日 命名（listed_{上市日期}、otc_{上櫃日期}），抓到同一天的資料只會覆寫同一個檔案；某個市場這輪抓取失敗（空清單）時不寫入該市場的快照與 SQLite，回報日期也改用本地既有的舊日期，讓日期不一致警示能正確顯示。isNewTradingDay 只影響 log 訊息，不決定是否寫檔。

靜默期內命中本地快照時，SyncResult.saved = false，啟動流程會優先使用 bootstrap_cache_{上市日期}.json 分析快取，免重新計算。

API 抓取與重試

市場API
上市openapi.twse.com.tw/v1/exchangeReport/STOCK_DAY_ALL
上櫃www.tpex.org.tw/openapi/v1/tpex_mainboard_daily_close_quotes
  • 每次請求附加時間戳參數與 Cache-Control: no-cache，避免中間層快取回傳舊資料。
  • 每個市場最多嘗試 3 次，每次 20 秒逾時，失敗後間隔遞增（1s、2s）再試；整趟同步上限 120 秒。

背景回前景自動同步

App 沒有常駐背景同步。BootstrapApp 監聽 AppLifecycleState.resumed，從背景回到前景時靜默執行一次 syncTodayData()（沿用白天靜默期護欄，非強制）：

  • 30 秒冷卻，避免快速切換 App 時連續打 API。
  • 只有真的抓到新資料（saved = true）才重新計算、寫入快取與 SQLite、更新畫面並執行訊號異動偵測；否則維持現有畫面，不顯示 loading 或錯誤。
  • 與手動重新整理共用同一把鎖：回前景時若手動刷新正在進行則直接略過；反之手動刷新遇到背景同步進行中，會等待最多 30 秒再執行。

離線模式

冷啟動流程任何一步拋出例外（典型為無網路），改載入本地最新一份 bootstrap_cache_*.json，並在畫面頂端顯示離線提示條；若本地連一份快取都沒有，顯示「首次開屏需要網路同步」錯誤頁。

手動重新整理

首頁右上角圖示按鈕與上述兩個提示條內的文字連結，都會觸發同一個 forceSync 流程：完全略過時間護欄、向 TWSE / TPEX 取最新資料、重新計算並寫回 SQLite。使用者不需等待任何時間窗口，隨時可自行取得最新狀態。

  • 若這輪有市場沒抓到新資料，以橘色 SnackBar 提示「上市／上櫃資料本次未成功更新，可能仍是先前資料」。
  • 整趟流程失敗時，以紅色 SnackBar 提示「重新整理失敗，請稍後再試」。

SQLite 歷史寫入重試

每次同步到新資料後，_saveHistoryToSqlite() 會把當日板塊指標寫入 SQLite（供 30 日走勢圖、大類 Sparkline 與領先雷達歷史摘要使用；板塊資金佔比異動改讀原始 JSON 快照，不依賴此表）。只寫入這輪真的抓到新資料的市場，並以該市場自己的交易日為 key：

市場寫入內容
上市上市大類板塊 → category_history；混合版 mainstreams / lifecycles → mainstream_history / lifecycle_history；上市輪動 → rotation_history
上櫃上櫃大類板塊 → category_history；上櫃輪動 → rotation_history

寫入失敗時最多重試 3 次（間隔遞增），並記錄失敗 log，不再靜默吞錯：

for (attempt = 1; attempt <= 3; attempt++) {
  try { // saveDailySnapshot 為 upsert，重試整個方法安全、不會重複
    await saveDailySnapshot(...);
    return;
  } catch (e) {
    log('SQLite 歷史寫入失敗（第 $attempt/3 次）');
    await delay(Duration(seconds: attempt));
  }
}

除錯 Log 頁面

首頁標題列右上角的 🐞 按鈕開啟 DebugLogPage。DebugLogService 在記憶體中保留最近 400 筆同步／啟動／SQLite 寫入事件（App 重啟即清空），頁面可即時查看、清除，或一鍵複製全部 log 到剪貼簿。

一鍵重置並重新抓取

DebugLogPage 內的重置按鈕，經確認對話框後執行 _resetAndResync()：

  1. 先以 forceSync 向 API 重新抓取；抓取失敗則直接中止，本機資料完全不動。
  2. 抓取成功後才清空：SQLite 全部 6 張表（含 watchlist、signal_snapshot）與 daily/ 目錄下所有 JSON（原始快照、分析快取、三大法人／融資融券歷史）。
  3. 把剛抓到的資料依市場重新寫回 listed_* / otc_*，重新計算、寫入快取與 SQLite，更新畫面。
重置後本地只剩一天資料，需要多日窗口的指標（CapitalFlow N 日均量、Mainstream 三日延續力、Lifecycle 趨勢、Rotation、資金佔比異動、30 日走勢圖）會暫時退化，需正常使用數個交易日重新累積。觀察清單也會被清空。

檔案說明保留
listed_YYYMMDD.json 上市上市個股快照最近 7 個檔案
otc_YYYMMDD.json 上櫃上櫃個股快照最近 7 個檔案
YYYMMDD.json早期舊格式，已不再讀寫—
bootstrap_cache_YYYMMDD.json啟動分析結果快取（以上市日期為 key；離線防禦），不含細類與個股明細最近 3 份
institutional_flow_history.json三大法人 30 日流向歷史最近 30 筆
margin_trading_history.json融資融券 30 日餘額歷史最近 30 筆

安裝與執行

前置需求

  • Dart SDK ^3.11.5（pubspec.yaml 的 environment 限制）與其對應版本的 Flutter SDK
  • Android Studio / Xcode（依目標平台）
# 1. 安裝套件
flutter pub get

# 2. 產生 Drift 程式碼（首次或修改 Table 後需執行）
dart run build_runner build --delete-conflicting-outputs

# 3. 執行
flutter run
首次啟動需要網路連線，App 會自動從 TWSE / TPEX 同步最新交易日資料。同步完成後可離線使用快取資料。三大法人籌碼與融資融券每次開啟首頁即時抓取，離線時不顯示這兩張卡片。

推播通知權限

  • iOS：首次啟動時系統彈窗請求通知權限
  • Android：透過 signal_changes_v1 頻道發送，無需額外設定

更新 Drift Schema

dart run build_runner build --delete-conflicting-outputs

同步更新 AppDatabase.schemaVersion（目前 V6）並在 onUpgrade 中加入對應 migration。
