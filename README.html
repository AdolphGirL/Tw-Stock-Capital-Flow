專案簡介

本 App 是一套專為台灣股市一般投資人設計的板塊資金流向監控與量化決策系統。

傳統看盤工具只告訴你今天哪支股票漲最多，但無法回答：

主力集中哪裡？
今日資金正往哪個板塊集中
週期在哪？
上漲是點火還是即將出貨
潛伏訊號？
股價底部但主力已悄悄建倉
今日異常？
統計上顯著異常的資金動向
資料來源：臺灣證券交易所（TWSE）/ 證券櫃檯買賣中心（TPEX）開放資料。所有運算皆在設備本地端執行，不上傳任何個人資料。

訊號異動通知

每次開啟 App 演算完成後自動執行，同時觸發 App 內 Dialog 與系統本地推播通知。

  1. 讀取個人觀察清單；若清單為空，完全跳過（零額外運算）
  2. 載入 signal_snapshot 表的上次訊號記錄
  3. 重新計算今日訊號，偵測升級（觀望→買進）或降級（持股→出清）
  4. 儲存今日訊號作為下次比對基準
  5. 若有異動：彈出 App 內 Dialog + 推送系統本地通知（iOS / Android）

核心演算引擎

1. CapitalFlowEngine — 個股資金流引擎

計算每支個股今日資金流分數，作為板塊層級計算的原子輸入。

── 成交量比（volumeRatio）───────────────────────────── volumeRatio = today.value / avg(N-day value) ── 動能分數（momentumScore）────────────────────────── volatility = (high − low) / close × 100 momentumScore = changePercent × 0.7 + volatility × 0.3 ── 延續分數（persistenceScore）─────────────────────── persistenceScore = today.changePercent × (positiveDays / totalDays) ── 綜合資金流分數（flowScore）──────────────────────── flowScore = volumeRatio × 0.35 + momentumScore × 0.40 + persistenceScore × 0.25 ── 流向判定 ──────────────────────────────────────────── flowScore > 1 → inflow flowScore < −1 → outflow → neutral

2. MainstreamEngine — 主流方向引擎

聚合個股至板塊層級，計算主流資金強度分數（需至少 3 天資料計算延續力）。

各市場獨立運行：上市 上市 的 MainstreamEngine 只處理上市股票，上櫃 上櫃 同理，確保跨市場板塊名稱不互相干擾。
flowScore = mean( changePercent × value/億, per stock ) persistenceScore = day1×0.5 + day2×0.3 + day3×0.2 (近3日衰減加權) diffusionScore = riseCount / totalCount × 100 leaderScore = leader.value/億 × 0.6 + leader.changePercent × 0.4 mainstreamScore = flowScore×0.35 + persistenceScore×0.30 + diffusionScore×0.20 + leaderScore×0.15 hotMoneyIn = flowScore > 0 AND diffusionScore > 45

3. TrendMetricsEngine — 趨勢指標引擎

對任意時序數列計算四個趨勢特徵，供 LifecycleEngine 使用。

slope = vₙ − v₀ (頭尾差) acceleration = (vₙ − mid) − (mid − v₀) (後段加速 − 前段加速) volatility = mean( |vᵢ − avg| ) stability = 100 − volatility

4. LifecycleEngine — 生命週期引擎

對每個板塊建立3條時間序列（分數/流量/擴散），透過 TrendMetricsEngine 取得趨勢特徵，依規則判定所屬生命週期階段。

市場獨立計算：上市與上櫃各自有一個獨立的 LifecycleEngine 實例（由 _runLifecycleForMarket 在 Isolate 中執行），避免同名板塊跨市場干擾。詳見 上市/上櫃分離架構。
優先階段判斷條件（簡）
1死亡 (Dead)score < 10 AND slope < 0 AND flow < 0
2退潮 (Decline)slope < 0 AND accel < 0 AND flow < 0
3出貨 (Distribution)score > 70 AND accel < 0 AND volatility > 15
4狂熱 (Euphoric)score > 85 AND diffusion > 75 AND volatility > 20
5主升 (Markup)score > 60 AND slope > 20 AND stability > 70
6擴散 (Expansion)diffusion > 45 AND slope > 10 AND flowTrend.slope > 0
7點火 (Ignition)accel > 5 OR flowTrend.accel > 0
8盤整 (Consolidation)（以上條件皆不符）

5. MomentumStrategy — 動量決策策略

① 結構性 SELL（最高優先，無條件出清） stage ∈ {distribution, decline, dead} ② BUY — 點火試單 stage == ignition AND hotMoneyIn AND acceleration > 0 ③ BUY — 主升全面加碼 stage ∈ {expansion, markup} AND hotMoneyIn AND diffusion ≥ 50.0 ④ HOLD — 鎖籌續抱 hotMoneyIn AND persistence ≥ 40.0 ⑤ SELL — 動能渙散（雙殺條件） !hotMoneyIn AND persistence < 40.0 ⑥ NEUTRAL — 盤整觀望

關鍵設計：SELL 需兩項同時惡化，避免在橫盤整理時誤殺部位。

6. RotationEngine — 輪動引擎

比較今日與昨日各板塊資金流分，計算資金在板塊間的搬移路徑。

diff = todayScore − yesterdayScore diff > 0 → 流入板塊 diff < 0 → 流出板塊 rotationScore = ( |outflow_diff| + |inflow_diff| ) / 2

7. RotationLeadingAnalyser — 領先分析器

inflowSum = Σ rotationScore（此板塊為流入方） outflowSum = Σ rotationScore（此板塊為流出方） feederCount = 有多少不同板塊正在向此板塊輸血 RNM = inflowSum − outflowSum RNM ≥ 45 AND feederCount ≥ 2 → 🟢 強力吸籌 RNM > 15 → 🍏 溫和流入 −15 ≤ RNM ≤ 15 → ⚪ 中性觀望 RNM < −15 → 🟠 派發風險 RNM ≤ −45 → 🔴 大量出逃

8. MarketSentimentEngine — 市場情緒引擎

hotMoneyStrength = mean( value/億 × changePercent, per stock ) score = riseRatio × 30 + strongCategoryCount × 8 + mainstreamAverage × 0.35 + hotMoneyStrength × 0.25 score ≥ 85 → 過熱警惕 score ≥ 65 → 資金樂觀 score ≥ 40 → 中性觀望 score ≥ 20 → 偏空悲觀 else → 市場恐慌

9. AnomalyDetector — 異常偵測（Z-score）

μ = mean( trendStrength, 最近 N 天 ) σ = std ( trendStrength, 最近 N 天 ) Z = ( today_trendStrength − μ ) / σ Z > +0.8 → 異常資金湧入（取前 8 名） Z < −0.8 → 異常資金流出（取前 8 名） 最少樣本：≥ 5 天 最大回溯：35 天
市場歸類修正：以 object identity（CategoryUiModel 物件參考）而非名稱字串判斷上市/上櫃，確保同名板塊（如「半導體業」）正確分流。

10. MultiTimeframeConfirmBadge — 多週期訊號確認

scores = getCategoryTrend(limit: 5) // 由舊到新 recentAvg = ( scores[n-1] + scores[n-2] ) / 2 olderAvg = mean( scores[0 .. n-3] ) weeklyUp = recentAvg > olderAvg BUY AND weeklyUp → ✅ 週期確認 BUY AND !weeklyUp → ⚠️ 逆週線 HOLD AND !weeklyUp → 週線降溫

11. StockScanner — 個股掃描器

closePosition = (close − low) / (high − low) intradayReturn = (close − open) / open × 100 命中 = changePercent > 0 AND closePosition ≥ 0.7 AND intradayReturn > 0

上市 / 上櫃分離架構 V6 新增

背景：TWSE（上市）與 TPEX（上櫃）API 更新時間不一致，往往差一個交易日。舊版以單一日期記錄兩市場，導致 SQLite 日期標籤混亂、Tab UI 資料互相干擾。

快照檔案格式

上市 TWSE
listed_1150722.json
只包含 market == listed 的股票
上櫃 TPEX
otc_1150723.json
只包含 market == otc 的股票

讀取時兩檔合併為單一 StockDaySnapshot 供分析引擎使用。舊格式 YYYMMDD.json（無前綴）透過 fallback 機制向下相容，升級後第一次啟動不會空白。

日期欄位拆分

欄位說明使用於
listedDateTWSE 上市交易日（YYYMMDD）首頁上市卡片、SQLite listed 寫入、Tab 日期標籤
otcDateTPEX 上櫃交易日（YYYMMDD）首頁上櫃卡片、SQLite OTC 寫入、Tab 日期標籤
date相容欄位 = max(listed, otc)舊版快取讀取時的 fallback

BootstrapAnalyzer 並行計算圖

Phase 1（並行，6 個 Isolate） 上市 _runLifecycleForMarket(listed) ─────────────┐ 上櫃 _runLifecycleForMarket(otc) ─────────────┤ 上市 _runRotationForMarket(listed) ─────────────┤ 上櫃 _runRotationForMarket(otc) ─────────────┤ → AppBootstrapResult _runCapitalFlow(snapshots) ───────────────────┤ _runMainstream(snapshots) ───────────────────┘ Phase 2（並行，2 個 Isolate，依賴 Phase 1 的 mainstreams） _runLifecycle(snapshots, mainstreams) ← 混合，供首頁訊號用 _runSentiment(snapshots, mainstreams)
為何需要獨立週期／輪動計算？ TWSE 與 TPEX 使用相同的板塊分類名稱（如「半導體業」同時出現在上市與上櫃）。若混合計算後以名稱過濾，同名板塊會同時進入兩個 Tab；RotationEngine 更直接以板塊名稱分組計算輪動分數，混合快照會把兩個市場的個股加權平均在一起，算出一個誰都不代表的失真分數。獨立計算後，每個 Tab 只含該市場的板塊與輪動資料，點擊導航也只開啟該市場的 CategoryUiModel。

資料同步與更新機制 NEW

背景：TWSE / TPEX 官方開放資料實際整理完成的確切時間點無法得知（可能傍晚就緒，也可能延到隔天）。與其用一個猜測的精確時間點決定何時抓取，不如鎖定「確定沒有新資料」的區間直接略過、其餘時間都允許嘗試，並讓使用者隨時能自行手動刷新取得最新狀況。

白天靜默期（07:00–19:00）

SyncManager.syncTodayData() 每次啟動 App 時執行，邏輯如下：

時段 / 條件行為原因
07:00–19:00（白天靜默期）略過 API 呼叫，直接使用本地快照台股收盤 13:30，此區間內確定不會有新收盤資料，是唯一有把握的判斷依據
19:00～隔日 07:00（靜默期以外）一律嘗試向 API 抓取官方實際整理完成時間不確定，抓不到新資料只是白跑一趟、不會寫壞本地資料，因此不再猜測精確時間點
本地資料超過 3 個日曆天無論在不在靜默期，強制向 API 同步避免連假／網路異常後資料一直停留在舊快照
手動刷新（forceSync）完全略過以上護欄，直接呼叫 API使用者主動要求最新資料時的最高優先權
抓取失敗或抓到舊資料都不會覆蓋本地已存在的正確快照——正確性由 isNewTradingDay 比對日期把關，時間護欄只負責「要不要嘗試」，不影響資料正確性。

兩個提示條各自獨立顯示、互不影響；日期不一致警示不受靜默期限制，只要偵測到 listedDate != otcDate 就會出現，並明確點名是上市還是上櫃的資料較舊（以定長日期字串字典序比較）。

手動重新整理

首頁右上角圖示按鈕與上述兩個提示條內的文字連結，都會觸發同一個 forceSync 流程：完全略過時間護欄、向 TWSE / TPEX 取最新資料、重新計算並寫回 SQLite。使用者不需等待任何時間窗口，隨時可自行取得最新狀態。

SQLite 歷史寫入重試

每次同步到新資料後，_saveHistoryToSqlite() 會把當日板塊指標寫入 SQLite（供 30 日走勢圖、異常偵測 Z-score 基準使用）。寫入失敗時最多重試 3 次（間隔遞增），並記錄失敗 log，不再靜默吞錯：

for (attempt = 1; attempt <= 3; attempt++) {
  try { // saveDailySnapshot 為 upsert，重試整個方法安全、不會重複
    await saveDailySnapshot(...);
    return;
  } catch (e) {
    log('SQLite 歷史寫入失敗（第 $attempt/3 次）');
    await delay(Duration(seconds: attempt));
  }
}

安裝與執行

前置需求

  • Flutter SDK ≥ 3.11.5 / Dart SDK ≥ 3.0.0
  • Android Studio / Xcode（依目標平台）
# 1. 安裝套件
flutter pub get

# 2. 產生 Drift 程式碼（首次或修改 Table 後需執行）
dart run build_runner build

# 3. 執行
flutter run
首次啟動需要網路連線，App 會自動從 TWSE / TPEX 同步最新交易日資料。同步完成後可離線使用快取資料。三大法人籌碼每次啟動即時抓取，離線時不顯示此卡片。

推播通知權限

  • iOS：首次啟動時系統彈窗請求通知權限
  • Android：透過 signal_changes_v1 頻道發送，無需額外設定

更新 Drift Schema

dart run build_runner build --delete-conflicting-outputs

同步更新 AppDatabase.schemaVersion（目前 V6）並在 onUpgrade 中加入對應 migration。
